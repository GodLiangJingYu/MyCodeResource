# 第一章 软件测试基础 - 复习笔记

## 1.1 软件测试的基本概念

### 1.1.1 软件测试的定义

**Glenford J. Myers 的观点：**
1. 软件测试是程序的执行过程，目的在于发现错误
2. 软件测试是为了证明程序有错误，而不是证明程序无错误
3. 一个好的软件测试用例在于能发现至今未发现的错误
4. 一个成功的软件测试是发现了至今未发现的错误的测试

**Bill Hetzel 的观点：**
- 软件测试是以评价一个程序或者系统属性为目标的任何一种活动
- 软件测试是对软件质量的度量

**IEEE 的定义：**
1. 在特定的条件下运行系统或构件，观察或记录结果，对系统的某个方面做出评价
2. 分析某个软件项以发现和现存的，以及要求的条件之差别（即错误并评价此软件项的特性）

### 1.1.2 软件测试的目的

1. **发现缺陷**：以最少的人力、物力、时间找出软件中潜在的各种错误和缺陷，全面评估和提高软件质量，及时揭示质量风险，控制项目风险

2. **过程改进**：有助于发现开发工作中所采用的软件过程的缺陷，通过对软件缺陷进行分析，获得软件缺陷模式，有助于软件缺陷预防，以便进行软件过程改进

3. **质量评估**：评价程序或系统的属性，对软件质量进行度量和评估，以验证软件的质量能否满足用户的需求

### 1.1.3 软件测试与软件质量保证

**软件质量保证（SQA）：**
- 贯穿软件项目整个生命周期的有计划的系统活动
- 经常针对整个项目质量计划执行情况进行评估、检查和改进
- 确保项目质量与计划保持一致
- 确保软件项目的过程遵循了对应的标准及规范要求

**软件测试与SQA的关系：**
- **共同点**：目的都是尽力确保软件产品满足需求，都贯穿在整个软件开发生命周期中
- **区别**：
  - 测试可以查找错误并进行修改，从而提高软件产品的质量
  - SQA可以通过测试避免错误以求高质量，并且还有其他方面的措施以保证质量
  - SQA的职能是向管理层提供正确的可行信息，从而促进和辅助设计流程的改进
  - SQA还包括监督测试流程

### 1.1.4 软件测试的必要性

**历史案例：**
1. **第一个软件缺陷**：1945年9月9日，Grace Hopper在马克二型计算机中发现一只飞蛾导致继电器故障，这是第一个有记载的软件缺陷

2. **波音公司星际客机软件故障**（2019年12月20日）：
   - 软件定时器异常导致飞船无法与国际空间站对接
   - 原因：软件编码错误，飞船在终端计数开始之前将时钟与火箭同步
   - NASA和波音联合调查小组确定了61项纠正和预防措施

3. **Uber自动驾驶汽车撞死行人**（2018年3月）：
   - 全球首例无人驾驶汽车致死案
   - 原因：系统检测、处理和决策的时间过长，夜间图像不清晰

### 1.1.5 缺陷、错误、失效的概念

**三个基本概念：**
- **缺陷（Fault）**：项目内的错误代码，有时称为defect或bug
- **错误（Error）**：程序运行时，因为执行到了错误代码而造成程序内部状态出错
- **失效（Failure）**：程序运行结束后，其实际结果与预期结果不一致

**示例分析：**
```java
// 第3行有缺陷
for (int i = 0; i <= x.length; i++)  // 应该是 i < x.length
    count++;
```

- 输入 `x = {1, 0, 2}`：执行到缺陷代码，但未造成错误，未产生失效
- 输入 `x = {0, 1, 2}`：执行到缺陷代码，造成变量count取值出错（错误），最终影响输出（失效）

**RIP模型（缺陷检测的必要条件）：**

要确保测试用例触发外在失效，需要满足以下3个必要条件：

1. **可达性（Reachability，R）**：测试用例必须执行到包含缺陷的语句
2. **传染性（Infection，I）**：缺陷语句执行后必须导致程序内部状态出现错误（某些变量的取值出现错误）
3. **传播性（Propagation，P）**：不正确的程序内部状态通过传播语句导致程序的实际输出与预期输出不一致

## 1.2 软件测试的分类

### 1.2.1 按测试阶段或测试步骤划分

- **单元测试**：对软件设计的最小单位（模块）进行测试
- **集成测试**：将多个模块组合起来进行测试
- **确认测试**：验证软件是否满足需求规格说明书的要求
  - **Alpha测试**：由开发者或内部测试人员进行
  - **Beta测试**：由用户在实际使用环境中进行
- **系统测试**：将软件作为一个完整的系统进行测试

### 1.2.2 按测试对象划分

- **单元测试**：测试单个模块
- **配置项测试**：测试配置项
- **部件测试**：测试部件
- **系统测试**：测试整个系统

### 1.2.3 按使用的测试技术划分

**静态测试**：不运行程序，通过分析代码、文档等发现问题

**动态测试**：运行程序，通过输入数据观察输出结果发现问题
- **白盒测试**：基于程序内部结构设计测试用例
  - 逻辑覆盖测试
  - 域测试
  - 程序变异测试
  - 路径测试
  - 符号测试
- **黑盒测试**：基于需求规格说明书设计测试用例
  - 功能测试
  - 强度测试
  - 边界值测试
  - 随机测试

### 1.2.4 按软件质量特性划分

- **功能性测试**：适合性、准确性、互操作性、安全性、依从性
- **可靠性测试**：容错性、成熟性、易恢复性、依从性
- **易用性测试**：易理解性、易学习性、易操作性、吸引性、依从性
- **效率测试**：时间特性、资源利用率、依从性
- **维护性测试**：易改变性、稳定性、易测试性、易分析性、依从性
- **可移植性测试**：适应性、易安装性、易替换性、共存性、依从性

### 1.2.5 按照测试项目划分

1. **功能测试**：验证功能是否符合需求
2. **健壮性测试**：验证软件对各种异常情况的处理能力
3. **恢复测试**：验证软件的恢复或重构能力
4. **人机界面测试**：测试人机界面的有效性、便捷性、直观性
5. **接口测试**：测试被测对象与其他软件或硬件的接口
6. **强度测试**：使软件在设计能力的极限状态下运行
7. **可用性测试**：对"用户友好性"的测试
8. **压力测试**：对系统不断施加压力的测试
9. **性能测试**：测试软件是否达到规定的各类性能指标
10. **兼容测试**：测试软件在特定环境下的性能
11. **用户界面测试**：测试系统的界面
12. **安全性测试**：测试软件在攻击下的处理能力
13. **可靠性测试**：对系统能否稳定运行进行估计
14. **安装测试**：检验软件是否可以正确安装
15. **文档测试**：测试开发过程中生成的文档

## 1.3 软件缺陷管理

### 1.3.1 软件缺陷的概念

满足以下任意一种情况都可以称为软件缺陷：
1. 软件未达到产品说明书中标明的功能
2. 软件出现了产品说明书中指明的不应该出现的功能
3. 软件功能超出了产品说明书中指明的范围
4. 软件未达到产品说明书中指明的应达到的目的
5. 软件难以理解和使用、运行速度慢或最终用户认为不好

### 1.3.2 软件缺陷的属性

1. **软件缺陷标识（Identifier）**：标记某个软件缺陷的一组符号，每个软件缺陷必须有唯一的标识

2. **软件缺陷类型（Type）**：根据软件缺陷的自然属性划分的种类
   - 功能错误
   - 用户界面错误
   - 数据访问错误
   - 性能错误
   - 初始化/终止错误
   - 文档错误
   - 编程标准错误
   - 安全性错误

3. **软件缺陷严重程度（Severity）**：因软件缺陷引起的故障对软件产品的影响程度
   - **致命（Critical）**：导致系统崩溃、数据丢失、安全漏洞等严重问题
   - **严重（Major）**：主要功能不能实现，但没有数据丢失
   - **一般（Normal）**：部分功能不能实现，但不影响主要功能
   - **轻微（Minor）**：对功能几乎没有影响，只是界面、提示等小问题
   - **建议（Suggestion）**：改进建议，不是缺陷

4. **软件缺陷优先级（Priority）**：软件缺陷必须被修复的紧急程度
   - **P1（紧急）**：必须立即修复
   - **P2（高）**：尽快修复
   - **P3（中）**：有时间就修复
   - **P4（低）**：可以延后修复

5. **软件缺陷状态（Status）**：软件缺陷通过一个跟踪修复过程的进展情况
   - **新建（New）**：缺陷刚被提交
   - **已分配（Assigned）**：缺陷已分配给开发人员
   - **已解决（Resolved）**：缺陷已被修复，等待验证
   - **已验证（Verified）**：缺陷修复已验证通过
   - **已关闭（Closed）**：缺陷已确认修复
   - **重新打开（Reopened）**：缺陷修复验证失败，需要重新修复
   - **无法复现（Cannot Reproduce）**：无法复现该缺陷
   - **不是缺陷（Not a Bug）**：不是真正的缺陷
   - **延期（Deferred）**：延期修复
   - **不予修复（Won't Fix）**：决定不修复

6. **软件缺陷起源（Origin）**：软件缺陷引起的故障或事件第一次被检测到的阶段
   - 需求阶段
   - 设计阶段
   - 编码阶段
   - 测试阶段
   - 运行阶段

7. **软件缺陷来源（Source）**：引起软件缺陷的起因
   - 需求错误
   - 设计错误
   - 编码错误
   - 配置错误
   - 文档错误

### 1.3.3 软件缺陷生命周期

软件缺陷拥有自己的生命周期，包括以下状态：
新建 → 已分配 → 已解决 → 已验证 → 已关闭

在修复过程中可能会出现：
- 重新打开（验证失败）
- 无法复现
- 不是缺陷
- 延期
- 不予修复

## 1.4 软件质量模型与软件测试相关特性

### 1.4.1 软件质量评价

通常从以下几个方面评价软件质量的优劣：
1. 软件需求是衡量软件质量的基础，不符合需求的软件就不具备质量
2. 软件结构良好，易读、易于理解，并易于修改、维护
3. 软件系统具有友好的用户界面，便于用户使用
4. 软件生存周期中各阶段文档齐全、规范，便于配置、管理

### 1.4.2 ISO/IEC 9126-1991 软件质量度量模型

该模型由3层组成：
- **第1层**：质量特性
- **第2层**：质量子特性
- **第3层**：度量

#### 6大质量特性：

**1. 功能性（Functionality）**
- 适合性：软件产品与指定的任务和用户提供一组合适的功能的能力
- 准确性：软件产品具有所需精确度的正确或相符的结果及效果的能力
- 互操作性：软件产品与一个或多个规定系统进行交互的能力
- 安全性：软件产品保护信息和数据的能力
- 依从性：软件产品遵循与功能性相关的标准、约定或法规的能力

**2. 可靠性（Reliability）**
- 成熟性：软件产品避免因软件中错误发生而导致失效的能力
- 容错性：在软件发生故障或违反指定接口的情况下，软件产品维持规定的性能级别的能力
- 易恢复性：在失效发生的情况下，软件产品重建规定的性能级别并恢复受直接影响的数据的能力
- 依从性：软件产品遵循与可靠性相关的标准、约定或法规的能力

**3. 可使用性（Usability）**
- 易理解性：软件产品使用户能理解它是否合适，以及如何能将软件用于特定的任务和使用环境的能力
- 易学习性：软件产品使用户能学习它的能力
- 易操作性：软件产品使用户能操作和控制它的能力
- 吸引性：软件产品吸引用户的能力
- 依从性：软件产品遵循与易用性相关的标准、约定、风格指南或法规的能力

**4. 效率（Efficiency）**
- 时间特性：软件产品执行其功能时，可以提供适当的响应时间和处理时间，以及吞吐率的能力
- 资源特性：软件产品执行其功能时，可以提供合适的数量和类型的资源的能力
- 依从性：软件产品遵循与效率相关的标准或约定的能力

**5. 可维护性（Maintainability）**
- 易分析性：软件产品诊断软件中的缺陷或失效原因，以及判定待修改部分的能力
- 稳定性：软件产品避免由于软件修改而造成意外结果的能力
- 易改变性：软件产品使指定的修改可以被实现的能力
- 易测试性：软件产品使已修改软件能被确认的能力
- 依从性：软件产品遵循与维护性相关的标准或约定的能力

**6. 可移植性（Portability）**
- 适应性：软件产品无须采用有别于为考虑该软件的目的而准备的活动或手段，就能够适应不同的指定的环境的能力
- 易安装性：软件产品在指定环境中被安装的能力
- 共存性：软件产品在公共环境中同与其分享公共资源的其他独立软件共存的能力
- 易替换性：软件产品在环境相同、目的相同的情况下替代另一个指定软件产品的能力
- 依从性：软件产品遵循与可移植性相关的标准或约定的能力

### 1.4.3 测试的复杂性和经济性

**三角形程序测试的复杂性：**

测试一个判断三角形类型的程序，需要考虑：
1. 合法的一般三角形
2. 合法的等边三角形
3. 合法的等腰三角形（3种排列方案）
4. 一条边长为0
5. 两条边之和等于第三条边（3种排列方案）
6. 两条边之和小于第三条边（3种排列方案）
7. 三条边都为0
8. 一条边长为负数
9. 边长不是整数
10. 边数不是3

经验丰富的专业程序开发人员平均只得7.8分（满分14分），说明即使简单的程序测试也不是一件容易的事。

**黑盒测试的复杂性：**

- 穷举输入测试：把所有可能的输入全部用作测试输入
- 例如：Microsoft Windows计算器，要穷尽测试所有可能的合法输入是不现实的

**白盒测试的复杂性：**

- 穷举路径测试：使程序中每条路径至少执行一次
- 程序的路径数量可能是天文数字
- 示例：一个由10~20条语句构成的程序，含有一个最多重复20次的循环语句，从A点到B点的所有路径数有5^20 + 5^19 + ... + 5^1
- 如果每5分钟可以写出、执行并验证一个测试用例，那么测试完所有路径大概要花10亿年

**穷举路径测试的局限性：**

1. 不能保证程序实现符合规格说明的要求
2. 不可能查出程序中因遗漏路径而出现的错误
3. 可能发现不了有关数据的故障

**Dijkstra的名言：**
"软件测试只能证明故障的存在，但不能证明故障不存在"

## 1.5 软件测试充分性和测试停止准则

### 1.5.1 软件的测试充分性问题

**1. 测试充分性准则**

测试充分性准则用来评价一个测试数据集按照规范说明测试被测软件是否充分。测试的充分性也可以通过"覆盖率"这一概念进行衡量。

**2. 覆盖率的测定方式**

- 基于软件规格说明：测试检测了其中的多少需求
- 基于程序源代码：测试检测了其中的多少行代码、多少条语句或多少条路径等

**3. 测试充分性准则的基本性质**

1. 空测试对于任何软件测试都是不充分的
2. 对任何软件都存在有限的充分测试数据集（有限性）
3. 如果一个测试数据集对一个软件系统的测试是充分的，那么再增加一些测试用例也是充分的（单调性）
4. 软件越复杂，需要的测试用例就越多（复杂性）
5. 测试得越多，进一步测试所能得到的充分性增长就越少（回报递减律）

**4. Weyuker测试数据集充分性公理**

- **公理2.1（非外延性公理）**：如果有两个功能相同而实现不同的程序，对其中一个是充分的测试数据集对另一个不一定是充分的
- **公理2.2（多重修改公理）**：如果两个程序具有相同的语法结构，对一个充分的测试数据集对另一个不一定是充分的
- **公理2.3（不可分解公理）**：对一个程序进行了充分的测试，并不表示对其中的成分都进行了充分的测试
- **公理2.4（非复合性公理）**：对程序各单元是充分的测试数据集并不一定对整个程序（集成后）是充分的

### 1.5.2 软件测试原则

**1. 完全测试程序是不可能的**

主要原因：
- 程序的输入量太大
- 程序的输出量太多
- 软件实现的途径太多

**2. 软件测试是有风险的**

- 不能做到完全测试，不测试又会漏掉一些软件故障
- 测试的目标应该是使有限的测试投资获得最大的收益
- 如何把无边无际的可能输入减少到可以控制的范围，以及如何针对风险制订出一些明智抉择

**3. 测试无法找到隐藏的软件故障**

- 通过软件测试可以查找并报告发现的软件故障
- 但不能保证软件故障全部被找到
- 也无法报告隐藏的软件故障

**4. 存在的故障数量与发现的故障数量成正比**

原因：
- 程序员怠倦
- 程序员往往犯同样的错误
- 某些软件故障可能是冰山一角

**5. 杀虫剂现象**

- 软件测试进行得越多，其程序免疫力越强
- 应该根据不同的测试方法开发测试用例，对程序的不同部分进行测试

**6. 并非所有软件故障都能修复**

不修复的原因：
- 没有足够的时间
- 修复风险太大
- 不值得修复
- 不算真正的软件故障

**7. 一般不要丢弃测试用例**

- 除非确实没有用，测试人员一般不要丢弃测试用例
- 保存测试用例可以用于回归测试

**8. 应避免测试自己编写的程序**

- 开发和测试是两个不同的活动
- 一个人不可能把两个截然对立的开发人员和测试人员角色都扮演好
- 由他人来进行测试可能会更有效、更成功

**9. 软件测试是一项复杂且具有创造性的和需要高度智慧的挑战性任务**

- 随着软件规模和复杂性的增加，测试一个大型软件所要求的创造力，可能超过设计那个软件所要求的创造力

### 1.5.3 测试停止准则

**实用的停止测试的标准：**

1. **第1类标准**：测试超过了预定的时间，停止测试
2. **第2类标准**：执行了所有测试用例但没有发现故障，停止测试
3. **第3类标准**：使用特定的测试用例方法作为判断测试停止的基础
4. **第4类标准**：正面指出测试完成的要求，如发现并修改70个软件故障
5. **第5类标准**：根据单位时间内查出故障的数量决定是否停止测试

### 作业一：基本路径测试方法

**题目**：给定一个求三个数最大值的程序

```
1. start: max = a
2. b > max?
3. max = b
4. c > max?
5. max = c
6. return max
```

#### 1. 控制流图（Control Flow Graph）

```
    [1] start: max = a
        ↓
    [2] b > max?
      ↙   ↘
    No     Yes
      ↓      ↓
    [4]    [3] max = b
    c > max?   ↓
      ↙   ↘   ↓
    No     Yes ↓
      ↓      ↓
    [6]    [4] c > max?
    return max  ↙   ↘
              No     Yes
                ↓      ↓
              [6]    [5] max = c
              return max   ↓
                          ↓
                        [6] return max
```

#### 2. 圈复杂度（Cyclomatic Complexity）

公式：V(G) = P + 1

其中 P 是判定节点（谓词）的数量

本题中有 2 个 if 语句（判定节点）

结果：圈复杂度为 3

#### 3. 独立路径（Independent Paths）

**路径1**：1 → 2 → 4 → 6
- 条件：b > max 为假，c > max 为假
- 说明：a 是最大值

**路径2**：1 → 2 → 3 → 4 → 6
- 条件：b > max 为真，c > max（此时max为b）为假
- 说明：b 是最大值，且 c 不大于 b

**路径3**：1 → 2 → 4 → 5 → 6
- 条件：b > max 为假，c > max 为真（即 c > a >= b）
- 说明：c 是最大值

#### 4. 测试用例设计

| 用例ID | 路径 | 输入 (a, b, c) | 预期输出 (max) | 覆盖说明 |
|--------|------|----------------|----------------|----------|
| 1 | 1-2-4-6 | a=5, b=3, c=1 | 5 | b<=a, c<=a |
| 2 | 1-2-3-4-6 | a=3, b=5, c=1 | 5 | b>a, c<=b |
| 3 | 1-2-4-5-6 | a=5, b=3, c=8 | 8 | b<=a, c>a |

### 作业三：条件覆盖和分支覆盖

**题目**：保险费计算程序

```java
double calculateInsurance(int age, boolean isSmoker, boolean hasDisease) {
    double premium = 1000.0;

    // 分支1
    if (age > 60 && isSmoker) {
        premium *= 2.0;
    }
    // 分支2
    else if (age > 30 && hasDisease) {
        premium *= 1.5;
    }
    // 分支3
    else if (age <= 30) {
        premium *= 0.8;
    }
    // （隐式分支4：上述条件均不满足）

    return premium;
}
```

#### 1. 程序分析

**原子条件（Conditions）：**
- C1: age > 60
- C2: isSmoker
- C3: age > 30
- C4: hasDisease
- C5: age <= 30（注：若 age>60 为假，age>30 为假，则 age<=30 必然为真）

#### 2. 测试用例设计（满足条件覆盖和分支覆盖）

**目标：**
- 条件覆盖：每个原子条件（C1-C5）至少取一次真（True）和一次假（False）
- 分支覆盖：每个 if 和 else（包括隐式else）路径至少执行一次

| ID | 输入 (age, isSmoker, hasDisease) | 预期结果 | 覆盖分支 | 覆盖条件 | 值 | 分析 |
|----|----------------------------------|----------|----------|----------|-----|------|
| TC1 | 65, true, false | 2000.0 | 分支1 | C1=T, C2=T | 满足 age > 60 && isSmoker |
| TC2 | 45, false, true | 1500.0 | 分支2 | C1=F, C3=T, C4=T | 满足 age > 30 && hasDisease |
| TC3 | 25, false, false | 800.0 | 分支3 | C1=F, C3=F, C5=T | 满足 age <= 30 |
| TC4 | 50, false, false | 1000.0 | 分支4（Fall-through） | C1=F, C3=T, C4=F | 所有 if 块均为假，执行默认路径 |

#### 3. 覆盖率检查

**分支覆盖率：**
- 分支1: TC1 ✓
- 分支2: TC2 ✓
- 分支3: TC3 ✓
- 分支4: TC4 ✓
- **结果：100% 分支覆盖**

**条件覆盖率：**
- C1 (age > 60): T(TC1), F(TC2/3/4) ✓
- C2 (isSmoker): T(TC1), F(TC2/3/4) ✓
- C3 (age > 30): T(TC2/4), F(TC3) ✓
- C4 (hasDisease): T(TC2), F(TC1/3/4) ✓
- C5 (age <= 30): T(TC3), F(TC1/2/4) ✓
- **结果：100% 条件覆盖**

## 重点总结

### 核心概念
1. **软件测试的定义**：发现错误的过程，不是证明程序无错误
2. **缺陷、错误、失效的区别**：缺陷是代码错误，错误是内部状态错误，失效是输出错误
3. **RIP模型**：可达性、传染性、传播性是缺陷检测的必要条件

### 测试分类
1. **按阶段**：单元测试、集成测试、确认测试、系统测试
2. **按技术**：静态测试、动态测试（白盒测试、黑盒测试）
3. **按质量特性**：功能性、可靠性、易用性、效率、维护性、可移植性

### 缺陷管理
1. **缺陷属性**：标识、类型、严重程度、优先级、状态、起源、来源
2. **缺陷生命周期**：新建 → 已分配 → 已解决 → 已验证 → 已关闭
3. **常见工具**：Bugzilla、BugFree、Quality Center、JIRA、Mantis、Launchpad

### 质量模型
1. **ISO/IEC 9126-1991**：6大质量特性（功能性、可靠性、可使用性、效率、可维护性、可移植性）
2. **测试复杂性**：穷举测试是不现实的，黑盒和白盒测试都有局限性

### 测试原则
1. 完全测试程序是不可能的
2. 软件测试是有风险的
3. 测试无法找到隐藏的软件故障
4. 存在的故障数量与发现的故障数量成正比
5. 杀虫剂现象
6. 并非所有软件故障都能修复
7. 一般不要丢弃测试用例
8. 应避免测试自己编写的程序
9. 软件测试是一项复杂且具有创造性的任务

### 测试方法实战
1. **基本路径测试**：
   - 绘制控制流图
   - 计算圈复杂度 V(G) = P + 1
   - 确定独立路径
   - 设计测试用例

2. **等价类划分**：
   - 分析输入条件
   - 划分有效等价类和无效等价类
   - 设计测试用例覆盖每个等价类

3. **条件覆盖和分支覆盖**：
   - 识别原子条件
   - 确定分支
   - 设计测试用例使每个条件和分支至少取一次真和假
