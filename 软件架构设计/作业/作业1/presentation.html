共享自习室预约管理系统

系统架构设计汇报

ARCHITECTURE & DESIGN

老师好，同学们好。今天我为大家汇报“共享自习室预约管理系统”的架构设计成果。 本项目旨在为高校提供一个自动化的自习室管理平台，解决座位资源紧张、占座不规范的问题。

1. 核心需求与业务全景

核心价值

  • 提升资源利用率：实时查看空闲座位，预约后方可使用
  • 规范现场秩序：扫描门禁签到，超时未达记录违约
  • 商业化闭环：支持付费预约，超时未支付自动释放

系统参与者

  • 自习者：核心用户，进行座位预约、支付与签到
  • 管理员：负责自习室信息维护、订单查询及异常处理
  • 外部系统：用户账户系统、支付系统、门禁系统
首先看核心需求。系统的核心价值在于解决自习室资源分配问题。 自习者通过系统预约座位并支付，到达后通过门禁签到。管理员负责后台维护。 同时，为了降低复杂度，我们将账户认证、支付、门禁控制交由外部系统处理。

2. 职责划分与架构分层

采用经典的面向对象四层架构设计，确保高内聚、低耦合。

边界类 (Boundary)

隔离外部系统与用户界面交互

ReservationUI, PaymentSystemInterface

控制类 (Control)

封装核心业务流程与用例逻辑

ReservationController, CheckInController

应用逻辑类 (App Logic)

高复用、易变的复杂业务规则提取

ConflictDetectionLogic, PricingLogic

实体类 (Entity)

系统核心数据与领域模型

Reservation, Seat, TimeSlot
在架构分层上，我们将其分为边界类、控制类、应用逻辑类和实体类。 特别说明一下“应用逻辑类”：我们将冲突检测、计费策略等易变、复杂的逻辑从Controller中剥离出来，封装在App Logic层，这样当计费规则改变时，不需要修改控制流。

3. 领域模型设计 (Static Model)

  • Seat (座位) 与 TimeSlot (时间段) 解耦物理座位与时间，避免直接锁定物理座位导致并发和资源浪费问题。
  • Reservation (预约单) - 核心聚合根
    • 关联 1 个 User 和 1 个 Seat
    • 占用 1..* 个 TimeSlot
    • 生命周期强关联 PaymentRecord 和 CheckInRecord
关于领域模型，最关键的设计是“预约与座位”的关系。 一个座位可以被多次预约（在不同时间段）。因此我们引入了TimeSlot（时间段）实体。预约单占用的是特定的时间段，而不是直接霸占物理座位，这为解决时间冲突提供了模型基础。

4. 核心用例：预约座位流转

  1. 触发：用户通过UI选择座位和时间，提交给 ReservationController
  2. 鉴权：调用 AccountSystemInterface 验证用户身份
  3. 防冲突：调用 ConflictDetectionLogic 检查目标 TimeSlot 是否可用
  4. 计费：调用 PricingLogic 计算总价
  5. 落库：创建 Reservation 对象，锁定时间段
  6. 收银：跳转支付系统，订单状态变更为 待支付
让我们看看最核心的“预约座位”交互流程。 用户提交请求后，ReservationController 充当协调者：首先通过边界类调用外部账户系统鉴权，接着调用 ConflictDetectionLogic 检查座位时间冲突，确认可用后调用 PricingLogic 计算价格，最后生成预约单实体并转向支付。整个流程各司其职。

5. 核心状态机：预约单生命周期

[*] ──▶ 【待支付】
          │
          ├──▶ 支付成功 ──▶ 【已预约】
          │                   │
          │                   ├──▶ 扫码入场 ──▶ 【已签到】──▶ 【已结束】
          │                   │
          │                   └──▶ 逾期未达 ──▶ 【已过期】──▶ 【已违约】(扣信誉分)
          │
          └──▶ 超时/主动 ──▶ 【已取消】 ──▶ [*]
订单的生命周期是系统状态管理的核心。 创建订单后进入“待支付”；15分钟内支付成功进入“已预约”； 到达自习室扫码后变为“已签到”；如果到时间未签到则变为“已过期”，随后被系统标记为“已违约”并扣除信誉分。 待支付状态超时未支付，会被AutoCancelController自动扫描并变更为“已取消”。

6. 关键设计决策解答

如何解决时间冲突？

不直接锁定 Seat。

引入 TimeSlot 实体，利用 ConflictDetectionLogic 遍历该座位已售出的时间段并执行 overlap() 交叉对比，确保并发安全与资源最大化利用。

为什么提取应用逻辑类？

计费规则、违约扣分规则（CreditPolicyLogic）等业务策略易变。

提取成独立类，可使 Controller 只关注流程流转，符合单一职责原则（SRP），提升系统可维护性。

最后回答一下架构设计中的几个关键决策。 第一，时间冲突怎么解决？我们通过TimeSlot重叠检测来避免冲突。 第二，为什么要提取应用逻辑类？因为像计费、信誉分扣除这样的规则会经常变动，剥离出来后，改规则不需要动Controller的核心流程，系统可维护性大大提升。
